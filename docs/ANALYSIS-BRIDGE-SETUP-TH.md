# เชื่อมระบบเจ้าของสำนวนกับส่วนวิเคราะห์

สถานะ 12 ตุลาคม 2569: เพิ่มโค้ดและหน้าจอส่ง–รับแล้ว ทดสอบครบวงจรด้วยทะเบียนจำลองและฐานวิเคราะห์ QA แยก ยังไม่ยืนยันกับฐาน/ที่เก็บเอกสารจริง ระบบทะเบียนในเครื่องตอบ HTTP 500 เพราะค่าที่จำเป็นไม่อยู่ในไฟล์ที่ dev โหลด ตรวจผ่าน Supabase connector พบโปรเจกต์เดิม `GPC-Legal-Decision-Drafting-Case-Management-System` (`tlqszhlggvoirhalsxge`) มีสถานะ `INACTIVE` ยังไม่ได้สั่ง restore หรือแก้ข้อมูลจริง

ไฟล์ `.env.local` ขาดค่าที่จำเป็น; `.env.prod` ไม่มี URL ฐานที่มี protocol ถูกต้อง; `.env.production.local` ชี้ `db.example.com` ซึ่งเป็น placeholder; `.env.bak` ชี้ Prisma Postgres บน localhost ที่เชื่อมไม่ได้ จึงยังไม่มีไฟล์ตั้งค่าที่ตรวจยืนยันว่าใช้ได้ ไม่ได้แสดง คัดลอก หรือหมุนเวียน secret

## ตั้งค่าก่อนใช้จริง

ผู้ดูแลต้องระบุฐาน Supabase เดิมและไฟล์ตั้งค่าที่ใช้งานได้ ไม่ส่ง secret ผ่านแชต ค่าที่ระบบทะเบียนต้องใช้ใน `C:\APP\.env.local` คือ `DATABASE_URL` (หรือ `POSTGRES_URL`), `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, และ bucket เดิมผ่าน `SUPABASE_STORAGE_BUCKET` (ค่าเริ่มต้น `case-documents`) คงรูปแบบยืนยันตัวตนของระบบเดิม ไม่เปลี่ยนเป็น AUTH_MODE=none เพื่อแก้ปัญหาการเชื่อม

`Start-Connected-Systems.cmd` ตรวจว่ามีค่าจำเป็นก่อนเปิดสองระบบบน loopback 3000 และ 4318 เป็นตัวเปิดในเครื่อง ไม่ใช่ deployment production เมื่อมีค่าแล้ว ยังต้องตรวจ `/api/health/db` และทดสอบบัญชี/Storage จริง ห้ามถือว่าการพบชื่อ env หมายถึง credential ใช้ได้ ไม่มี schema migration ที่ต้องรันสำหรับจุดเชื่อมนี้

## ใช้งาน

หน้าโฮมส่วนวิเคราะห์อยู่ `http://127.0.0.1:4318/` เป็นแดชบอร์ดงานในเครื่อง ส่วนรายการและตัวแก้งานอยู่ `/analysis` แยก เมนู “รับงานจากสำนวน” อยู่ `/intake`; ลิงก์ handoff เดิมยังรองรับ ทะเบียนเพิ่มทางเข้า “ระบบวิเคราะห์ (ในเครื่อง)” โดยไม่ส่งข้อมูลสำนวนเอง ต้องเลือกสำนวน/เอกสารตามขั้นตอนข้างล่างเมื่อจะส่งงาน

1. เปิดสำนวนในระบบทะเบียน กรรมการ/นิติกรเห็นจุดเชื่อมเฉพาะสำนวนที่รับผิดชอบ ส่วน admin ใช้สำนวนที่เข้าถึงได้
2. กรอกข้อความที่จะส่งและเลือกเอกสาร ไม่มีการส่งทุกไฟล์อัตโนมัติ กด “จัดชุดส่งวิเคราะห์”
3. กด “เปิดและส่งไปส่วนวิเคราะห์” ตรวจชื่อเรื่อง เลขสำนวน ข้อความและรายการเอกสาร แล้วกดยืนยันรับเข้า เป็นสำเนาเฉพาะงาน เอกสารยังไม่ถูกอนุมัติข้อความโดยอัตโนมัติ
4. ตรวจหลักฐาน/แหล่ง แก้ร่าง และบันทึกฉบับตามขั้นตอนส่วนวิเคราะห์
5. แท็บส่งออก เลือกฉบับ กด “จัดชุดผลส่งกลับ” แล้ว “ส่งไปหน้าสำนวนที่เปิดไว้”
6. ที่ทะเบียน ตรวจร่างและยืนยันแนบ ระบบเก็บ Word และรายงานพร้อมที่มาเป็น CaseDocument สถานะ `analysis_draft_needs_review` ไม่แก้เจ้าของ สถานะทางราชการ หรือข้อความร่างเดิม ส่งฉบับเดิมซ้ำไม่แนบซ้ำ

ถ้าหน้าต่างเดิมปิด ใช้ไฟล์ชุดส่งงาน/ชุดผล `.json` แทนได้ รับงานที่เมนู “รับงานจากสำนวน” และรับผลที่หน้าสำนวนเดิม ห้ามแก้ JSON ระหว่างทาง Hash ใช้ตรวจความครบถ้วน ไม่ใช่ลายเซ็นรับรองความถูกต้องทางกฎหมาย การรับผลตรวจประวัติส่งงานเดิม เลขสำนวน รหัสชุด และ hash ของ Word อีกครั้ง

## ขอบเขตและข้อจำกัด

- ข้อมูลหลัก/กรรมการ/สถานะอยู่ที่ทะเบียน; ฐานอ้างอิงและงานวิเคราะห์อยู่ใน SQLite แยก การเพิ่มเอกสารผลเป็นการแนบที่ผู้ใช้ยืนยัน ไม่ใช่การรวมฐาน
- ส่งได้เฉพาะไฟล์ต้นฉบับที่อยู่ใน bucket ของสำนวนที่เลือก รวมไม่เกิน 20 MB ลิงก์ภายนอกแสดงให้แนบต้นฉบับแยก ไม่ดาวน์โหลด URL ใด ๆ อัตโนมัติ รูปแบบไฟล์ต้องตรงชนิดที่ส่วนวิเคราะห์รองรับ
- การรับผ่านหน้าต่างตรวจทั้ง origin และหน้าต่างต้นทาง ไม่เปิด CORS API ของส่วนวิเคราะห์ ทะเบียน local ต้องเป็น 127.0.0.1:3000 หรือ localhost:3000 หากเปลี่ยนที่อยู่ต้องกำหนด `ANALYSIS_REGISTRY_ORIGINS` ฝั่ง server วิเคราะห์ให้ตรงอย่างชัดเจน
- รุ่นนี้ตรวจแบบ local ยังไม่ยืนยันการใช้งานทะเบียนที่ deploy บน Vercel หรือข้อจำกัดขนาด request ของ hosting หากย้ายไป cloud ต้องตรวจข้อจำกัดก่อน ไม่อ้างว่าไฟล์ 20 MB ใช้ได้กับทุก hosting
- API ฝั่งทะเบียนตรวจสิทธิ์เฉพาะการส่ง/รับและเจ้าของสำนวน มีการตรวจซ้ำพร้อม row lock ใน transaction แนบผล หาก Storage หรือ transaction ล้มเหลว หยุดและพยายามล้างเฉพาะไฟล์ที่สร้างในรอบนั้น
- ระบบทะเบียนเดิมมี MVP auth ที่คืน `none` ตายตัวและใช้ผู้ใช้ admin จึงยังไม่ใช่ระบบหลายผู้ใช้ที่ยืนยันตัวตนจริง การตรวจเจ้าของและสิทธิ์มีในจุดเชื่อม แต่ในโหมดเดิมผู้ใช้จะเข้าทาง admin ตัวเปิดบังคับ loopback และ API จุดเชื่อมยอมรับ origin เฉพาะ 127.0.0.1:3000 / localhost:3000 ไม่เปิดผ่านเครือข่ายหรือ cloud ในรุ่นนี้ ตั้ง AUTH_MODE อย่างเดียวไม่แก้ข้อจำกัดนี้
- ผลทุกฉบับเป็นร่างรอตรวจ ส่วน AI ยังรอ API key ที่ได้รับอนุมัติ การเชื่อมสองระบบไม่เปิด AI หรือส่งข้อมูลไป OpenAI เอง

## หลักฐานการตรวจ

TypeScript ของระบบเดิมและ Vite build ผ่าน; unit 13 tests ผ่าน; integration เดิม 19 สถานการณ์และชุด transfer integration ผ่าน Browser ของ Codex ทดสอบคอมโพเนนต์ทะเบียนจริงกับ repository/Storage จำลองที่พอร์ต 4320 ส่งไป API วิเคราะห์จริงที่ 4319 แล้วส่งร่างกลับ กดยืนยันแนบได้ 1 ฉบับ โดยสถานะสำนวน unchanged ไม่ได้เขียน Supabase จริง

ยังต้องตรวจ credentials, สิทธิ์บัญชีจริง, bucket, และการแนบกลับฐานจริงก่อนกล่าวว่าเชื่อมใช้งานจริงพร้อมทั้งหมด การเลือกไฟล์ JSON ผ่าน file chooser และการ deploy ยังไม่ได้ตรวจในรอบนี้
